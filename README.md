# Paint Retail SaaS

Multi-store, multi-brand paint dealer platform for India. Product plans live in the
[roadmap repo](https://github.com/Avali-Tech/paint-retail-saas-roadmap).

## The first rule: every line of code is tested

- **Unit tests** (`src/**/*.test.ts`) cover logic in isolation: no network, no database.
- **Integration tests** (`src/**/*.int.test.ts`) run against a real PostgreSQL 17 in Docker
  (Testcontainers), with real S3-compatible storage (SeaweedFS) and real ClamAV for documents.
  No database mocks.
- Coverage across both suites must stay at **100%** for statements, branches, functions and
  lines. The run fails otherwise, locally and in CI.
- New code and its tests land in the same commit.

```sh

```

## Run the API locally

```sh
docker compose up -d                        # PostgreSQL (55432), S3 (58333), ClamAV (53310), Mailpit (58025); PAINT_*_PORT moves them
cp apps/api/.env.example apps/api/.env
pnpm --filter @paint/api build
pnpm --filter @paint/api start              # http://localhost:3000
curl localhost:3000/health/ready            # {"status":"ok","checks":{"database":"up"}}
```

`GET /health` answers while the process runs (liveness). `GET /health/ready` also checks
PostgreSQL and answers 503 when it is unreachable (readiness).

## Run the web app locally

The web app (`apps/web`, React + Vite, installable as a PWA) calls the API at `/api/...` on its own
origin; Vite forwards that to the API, so the API needs no CORS. Production puts the same rule in the
CDN or load balancer (or set `VITE_API_BASE_URL` at build time).

```sh
pnpm --filter @paint/api start              # API on http://localhost:3000 (see above)
pnpm --filter @paint/web dev                # http://localhost:5173, /api proxied to :3000
API_URL=http://localhost:4000 pnpm --filter @paint/web dev   # a different API
pnpm --filter @paint/web build && pnpm --filter @paint/web preview   # production build + service worker
```

With `SMS_PROVIDER=log` in `apps/api/.env`, sign-in codes for **Mobile code** sign-in appear in the
API's console.


Docker Desktop works instead of Colima (`brew install --cask docker`, open it once; it includes
Compose). **Moving from Docker Desktop to Colima:** Docker Desktop leaves `"credsStore": "desktop"`
in `~/.docker/config.json`, and every image pull then fails with `docker-credential-desktop:
executable file not found`. Delete that line (`pnpm demo` checks for it and says so).

**Every time:**

```sh
pnpm demo            # checks prerequisites, starts PostgreSQL, S3 storage and Mailpit, creates the
                     # bucket, builds, migrates, seeds if empty, starts the API and the web app,
                     # then prints the address and the sign-in sheet. Ctrl-C stops the app.
pnpm demo --fresh    # the same, re-creating the demo data first (do this on the morning of a demo)
pnpm demo:stop       # stops the Docker services; the data is kept
pnpm demo:reset      # drops the demo database and seeds it again (stop `pnpm demo` first)
pnpm demo:seed       # seeds only if the demo database is empty
```

off by default: uploads are refused until you start with `pnpm demo --clamav`. Notification

http://localhost:58025. Ports can be moved if something else uses them:
`DEMO_API_PORT=3100 DEMO_WEB_PORT=5200 pnpm demo` (and `PAINT_POSTGRES_PORT`,
`PAINT_STORAGE_PORT`, `PAINT_MAIL_PORT`, `PAINT_SMTP_PORT`, `PAINT_CLAMAV_PORT` for the services).

**A large shop, for performance testing (not for client demos).** `DEMO_SIZE=large pnpm demo

It also adds the books of 1,200 credit customers: about 15,000 bills on account, 6,000 payments,

`postStockMovementsInBulk` (balances always equal the ledger), and every document number series
continues. Timings and how they were measured: [docs/performance.md](docs/performance.md).

**Two-factor sign-in.** Owners and organization admins (when their business requires it, the
default) add an authenticator app at their next sign-in: a QR code plus the setup key, then ten
recovery codes to copy or download, shown once. Later sign-ins ask for a code from the app or a
recovery code. **Account security** (`/settings/security`, everyone) turns it on or off and renews
recovery codes; owners and admins set the business rule there; owners reset a member's
two-factor sign-in from the member's page under **Team**. The e2e tests act as the authenticator app with
`apps/web/e2e/totp.ts`.

**Theming (white-label).** Every colour, radius, spacing step, shadow and the font is a CSS custom
property derived at runtime from a business's branding (`appName`, `primary`, `accent`, `mode`,
`radius`, `density`, `font`) by `deriveTheme()` in `@paint/shared`, which also enforces WCAG AA
contrast. Components (`packages/ui`) and screens use only these tokens; `theme-guard.test.ts` fails
the build if a colour literal appears in their sources. Try it at **Settings → Appearance**
(`/settings/appearance`, owners and admins). Saving stores it for the whole business
(`PUT /organization/branding`) and shows the readability adjustments the server made; every
member's app loads it when they sign in, and keeps the last one on the device for a branded,
offline-ready first paint.

**Screens.** Customers (`/parties`: search, role filter, add and edit with the GSTIN checked as you
type and the duplicate warning), the customer 360 (`/parties/:id`: contact, credit, loyalty points
and history, activities, leads, opportunities, projects, contracts, documents), credit requests
(`/credit-requests`), credit rules (`/settings/credit`) and the loyalty programme
(`/settings/loyalty`), leads (`/leads`: filters, a pipeline board by stage with counts and values in
lakh/crore, stage moves from each card's menu, convert to an opportunity), opportunities
(`/opportunities`: weighted pipeline, won/lost with a reason, start a project), projects
(`/projects`: site, stage, architects/contractors/painters/dealers), each of these detail pages with
its activities (log a call, visit or note, schedule a follow-up), my follow-ups (`/follow-ups`:
overdue, today and upcoming in India time; mark done with the outcome and the next step,
reschedule; managers pick a colleague or everyone, and a store, and see who each is assigned to;
the dashboard's tile counts them the same way), activities (`/activities`: every record the member
can see, or one record's timeline, with record type, type, person and date filters applied by the
API), contracts (`/contracts`: type, status, party and "renewal due in N
days" filters; create, edit, activate, terminate with a reason, renew; their documents), reports
(`/reports`: filters built from the API's description, translated column headers, a paged table
and CSV), documents (`/documents`: every document on the records the member can see, filtered by
record, kind, uploader and day) and on the customer 360, contracts and projects
(`src/documents/DocumentsPanel.tsx`, for any record type: upload checked before sending, refusals
explained by their `code`, download under the server's file name, delete). The customer 360 links
to all of a party's leads, opportunities, projects and contracts, and members with all-store access
merge a duplicate into the record that stays ("Merge into…", with the rules shown and refusals as
the API gives them). Brands & categories (`/products/setup`) deactivates and reactivates categories;
the product form offers only categories that take new products. Salesperson pickers on leads,
opportunities, projects, contracts and follow-ups list who may take the record
(`GET /members/assignable`), also for roles that cannot see the team. **Team** (`/team`,
`members:read`): everyone with role, stores, status and two-factor sign-in; add a person
(`/team/new`), and on each member's page (`/team/:id`) change role and stores, deactivate or
reactivate, and (owners) reset two-factor sign-in, with the API's anti-escalation refusals shown as
they come. **Roles** (`/team/roles`): system and custom roles; custom roles are created and edited
with a permission checklist grouped by area (`roles:manage`), system roles are read-only, and
permissions the editor lacks are greyed out. Actions show only to roles that may use them. Each
screen is its own chunk (`React.lazy`), loaded when first opened. Features keep their routes
(`src/<feature>/routes.tsx`), navigation entries (`src/<feature>/nav.ts`) and messages
(`src/i18n/en-<feature>.ts`) in their own files.

**Platform console** (`/platform`, `src/platform`): the operators' own sign-in (password, then an
authenticator app added with a QR code at the first sign-in) and session, kept under its own storage key
(`paint.platform-session`) with its own API client, so an operator's token and a business member's never
stand in for each other. It always shows the product's default look, never a business's branding, in a
plain frame marked "Platform console". **Businesses** (`/platform/tenants`: search, status, plan, stores and
team against the plan's limits, last sign-in), a **business** (`/platform/tenants/:id`: usage and owners,
change plan, turn features on or off or back to the plan, suspend with a reason and a confirmation or
reactivate, ask for support access with a reason and a length), **Support access** (`/platform/support`:
requests waiting or running; open the read-only view, end access) and the **Access log**
(`/platform/access-log`: every request, decision and end). There is no operators screen: the API has no
routes to manage operators beyond the one-time bootstrap. **Open read-only view** opens the business's
app in a new tab with the support session handed over in the address fragment (never sent to a server);
that tab keeps it in its own `sessionStorage`, so it never replaces a business session on the device, and
shows a "Support view – read only" banner. The handed-over session must be platform support's: once `/auth/me` answers,
any other session (a forged link carrying someone's own account) is ended before anything shows, and the
sign-in page says the link was not a valid support view. Support views keep the product's own look. On the business's side, **Settings → Support access**
(`/settings/support`, `organization:manage`) approves or declines requests (who asked, why, for how long),
ends running access, and lists earlier requests; each request's page (`/settings/support/:id`, the link
in the notification) shows every request support made with it. Owners and admins see a banner on every
page while support access runs or a request waits.

**Party ledger and quote PDF** (MVP 2 follow-up C): a party's account (`/parties/:id/ledger`, `sales:read`, linked from the customer 360) lists date, document (linking to the invoice, note or payment), debit, credit and running balance, a page at a time with each page's opening and closing balance and a date filter. The quotation page's **Download PDF** fetches `GET /quotations/:id/pdf` in the member's language, and **Share on WhatsApp** opens `wa.me` with a short message; the PDF is attached by hand, as there are no public links to it yet.

**Receivables and statements** (MVP 3, P2-M10 and P2-M12): a pure ageing engine (`packages/shared/src/receivables`) ages what parties owe as of any day from their due dates, exactly as the party ledger has it ([docs/mvp-3/receivables-and-statements.md](docs/mvp-3/receivables-and-statements.md)). The **Receivables** screen (`/receivables`, `receivables:read` since round 2a) shows the dashboard figures, who owes most, and the ageing by customer, salesperson or store, each customer linking to its ledger and statement, with a CSV; the dashboard has a receivables tile. A customer's **Statement** (`/parties/:id/statement`, `sales:read`, linked from the customer record and the ledger) shows the period's A4 statement in English, or with Hindi or Telugu labels, to print, download as PDF, or **Share on WhatsApp**: a `wa.me` link with a short message, the PDF saved at the same moment to attach.

**Subscriptions** (P2-M08, [docs/mvp-3/subscriptions.md](docs/mvp-3/subscriptions.md)): a business signs up on a free trial (`SUBSCRIPTION_TRIAL_DAYS`, 14) and its owner sees the plan, usage, trial days and our invoices under **Settings → Billing** (`/settings/billing`): plans priced per store, monthly or annual, GST at 18% (placeholder prices); a plan is refused while the business uses more than it allows. **Manual invoicing is the default** (`SUBSCRIPTION_GATEWAY=manual`): the owner asks for a plan, a platform operator applies it in the console, which raises the platform's GST tax invoice (`PRS/26-27/000001`, SAC 998315 pending a CA, a PDF with the platform's bank account and UPI id), and records the bank transfer or UPI payment (amount, date, mode, reference), which starts or extends the plan; each next period's invoice is raised by the worker a week before the paid period ends. Unpaid past the paid period, the business has `SUBSCRIPTION_GRACE_DAYS` (7), then it is read-only, as it is once a trial or subscription ends; the shell warns the owner. A Razorpay Subscriptions adapter and a fake one stay behind config, on a payment-gateway port shared with P2-M32 (`apps/api/src/payments-gateway`: HMAC-checked webhooks, each event stored and applied once). In the demo, Sharma Paints pays our Standard monthly invoice by bank transfer and **Reddy Colour Centre** (owner Srinivas Reddy, 9000000201, mobile code) is on its trial.

**Colorant stock** (MVP 3 round 8a, [docs/mvp-3/colorants.md](docs/mvp-3/colorants.md)): colorants are products of type Colorant stocked loose, by the ml or by the g (a size / pack of 1 ml or 1 g, with its density in g per ml). A tint formula row may name the colorant it is dosed from (**Colorant N taken from**), and as the tinted packs leave, on invoice issue or on dispatch, the dose leaves stock as `tint_use` movements: ml and g convert through the density, shots and Y through the business's machine units (**Settings → Tinting**, `/settings/tinting`, one shot and one Y in ml). Short stock never stops the bill: what the store has is taken, the movement notes the shortfall, and the store's `inventory:manage` members get a `colorant_short` notification. Colorant is not given back on cancel or return. Migration 0092.

**Invoice print** (MVP 2 round 2b, [docs/mvp-2/print.md](docs/mvp-2/print.md)): `buildInvoiceView()` in
`@paint/shared` turns the GST engine's invoice and the document's header data into a print-ready view
that decides which Rule 46 fields the case needs; the web app prints it on A4 and 80 mm thermal paper
(`src/print`, previewed with sample data at `/print-preview`), `renderThermalText()` gives 48-column
text, and the API draws the A4 PDF with pdfkit and bundled Noto fonts (`apps/api/src/print`).

**Languages.** The web app speaks English, Hindi and Telugu. Each person picks theirs on the
sign-in page or under **Account security → Language**; it is kept on the device (`paint.locale`;
the API has no per-user language yet) and sets `<html lang>`. Numbers, money and dates keep the
Indian format with Latin digits in every language, and a Noto font for Devanagari or Telugu is
loaded behind the business's chosen font. Each `en-<feature>.ts` has `hi-<feature>.ts` and
`te-<feature>.ts` with exactly its keys (TypeScript and `translations.test.ts` check keys and
`{placeholders}`); counts use `{ one, other }` messages through `plural()`. The Hindi and Telugu
texts are drafts awaiting a native speaker's review: see
[docs/translations/glossary.md](docs/translations/glossary.md).

`E2E_CLAMAV=1 pnpm test:e2e` also starts S3-compatible storage and ClamAV and runs the full upload,
download and delete flow (about 1.5 GB of memory and a minute or two more).

**Access model:** `User → Role → Permissions`, plus store access (`all stores` or a list). Permission
keys and the standard roles live in `packages/shared/src/permissions.ts`. Routes declare
`@RequirePermissions(...)`; store-level checks happen in services with `can(auth, permission, storeId)`.

**No one can hand out more than they hold:** not permissions they lack, not stores they can't
access, not all-store access unless they have it, and not ownership unless they are an owner. The same
goes for custom roles: system roles are fixed, and nobody puts a permission they lack into a role,
changes a role that grants more than they hold, or changes the role they hold themselves
(`apps/api/src/members/role-rules.ts`). Nobody
can change their own access, which also keeps at least one active owner. Rules live in
`apps/api/src/members/access-rules.ts`.

**Parties** (roadmap §3.5–3.7): one record per person or business with any number of roles.
GSTINs are checked with the GSTN check character; the PAN is filled from the GSTIN. Parties with a
home store are visible to that store's staff; parties without one (suppliers, architects) are
business-wide.

**Tax & GST** (MVP 2, Sell & Bill; Settings → Tax & GST, `tax:read` to see, `tax:manage` to change,
owners and admins): GST is registered per state, so each store has its registration: type (regular,
composition or unregistered), GSTN state code, GSTIN (checksum checked, and it must start with the
state code), legal name (defaulting to the business's) and trade name, address. Every GSTIN of a
business carries one PAN, which the business shows as its own. Tax categories hold the GST rate in
basis points (1800 = 18%) with effective-from and effective-to dates: a change in law is a new rate from
a date (today or later), which closes the previous period; past rates are never edited (a trigger and
column grants refuse it, and periods cannot overlap). Every business starts with Paints 18% (the
default), Varnishes & wood finishes 18%, Putty & fillers 18%, Brushes & rollers 18%, Tools 18% and
Exempt, as of CBIC Notification 9/2025-Central Tax (Rate), in force from 22 September 2025
(`seed_default_tax_categories`, migration 0052; to be confirmed by a CA before the first invoice).
Each product has an HSN code (4, 6 or 8 digits) and a tax category; products get the default until a
store is registered, and from then on a new product needs one picked. Existing products were given the
category matching their catalogue category's name (putty, varnish/wood, brush/roller, tool), else
their product type, else Paints 18%, always keeping the rate they had (a "GST n%" category is added for
a rate no default carries). Customers have a place of supply (state code): taken from the GSTIN when
there is one, chosen otherwise. Changes to registrations, the legal name, categories, rates and a
product's HSN or tax category are in the audit log; the defaults a business starts with are not.

**Invoices and bills of supply** (MVP 2 round 2a; `docs/mvp-2/sell-and-bill.md`): a regular store
issues a tax invoice, a composition store a bill of supply without tax (never inter-state). Issuing
computes tax with the GST engine (`@paint/shared`, per line, half up, rounded to the rupee with a
round-off) from the tax category rates in force on the issue date (India time, from the database
clock): CGST + SGST when the place of supply is the store's state, IGST otherwise. The place of
supply is the buyer's GSTIN state for a registered buyer, else the delivery state, the buyer's
recorded state, or the store's. Each document keeps a snapshot of the supplier, buyer, HSN, unit,
rate and tax, its GSTR-1 class (B2B, B2C large over ₹1 lakh inter-state, B2C small) and tax per HSN
and rate. Numbers are gap-free per GSTIN, financial year, kind and prefix (`nextDocumentNumber` in the
issuing transaction; a refused issue gives its number back), and unique per GSTIN and year. An
issued document is never edited or deleted (a trigger allows only cancelling it, filling the IRN once
and the ITC status); its lines, tax rows and links change only while it is a draft. Issue refuses: an
unregistered store; HSN codes shorter than the GSTIN's turnover band needs; an unregistered buyer's
missing name, address or state from ₹50,000 of taxable value (Rule 46(e)); and a B2B invoice without
an IRN once the GSTIN's e-invoice date has passed. Walk-in sales go to a walk-in customer created with
the first one. The party ledger is append-only (`postPartyLedger` keeps `party_balances` equal to it);
party merges refuse a duplicate with invoices. Status changes, series, settings and GSTIN profiles
are in the audit log. Migrations 0054–0056 (the 0056 data migration grants `sales:read` and
`billing:issue` to owners, admins, branch managers, sales executives and store employees, and
`billing:cancel` to owners, admins and branch managers).

**Returns, credit and debit notes** (MVP 2 round 3c; spec §2.9, §4.5): a return takes goods back
against an issued invoice or bill of supply, each line to stock (`sale_return`) or written off
(`sale_return` then `damage`, both in the stock ledger), never more than sold less already returned
(the invoice is locked, so two returns cannot both take its last units). Its credit note reverses
each line's tax at the invoice's rate in proportion to the units (the GST engine's
`computeReturn`), so a full return, in one note or several, reverses the invoice's tax exactly.
Credit notes for a discount (only under a scheme agreed before the sale, s.15(3)(b)), an
overcharge or deficient goods, and debit notes for an undercharge, tax a value at the invoice
line's rate (`computeAdjustment`); a line is never credited more than its taxable value plus its
debits. Notes are numbered in the store's own series per kind (`AMPC/26-27/00001`,
`AMPD/26-27/00001`), gap-free, linked to the invoice (`note_of`), immutable once issued, and post
one party-ledger entry (credit − total, debit + total); a refund of money is round 3a's. Credit
notes are refused after 30 November following the end of the invoice's financial year (s.34(2));
the invoice shows the deadline and warns 30 days before. A B2B credit note records its buyer's
input-credit reversal as `unknown` (s.34(2) proviso from 1 Oct 2025, filled in 2.3). Credit notes
call a loyalty reversal hook that takes back points in proportion to the value credited once
invoices earn points (round 4a). Returns and notes need `billing:notes`. Web: **Invoices** (`/invoices`, read-only, with "Return items" and
"Credit / debit note" previewing the tax with the engine) and **Credit & debit notes** (`/notes`).

**Catalogue** (roadmap §3.11): one product family (e.g. Apex Ultima) with a variant per pack
size, each with its own SKU, MRP and selling price in paise, and barcodes. Hardware sold by the
piece is one product too: an optional variant `label` ("2 inch", "Grit 120", "48 mm", "Red")
tells same-sized packs apart, so a product has one variant per size, unit and label (no label
counts as one; case does not matter). Everywhere a variant is named (search, documents, exports,
the app) it reads "10 l" without a label, just the label for a single piece ("Paint Brush 2
inch"), and label then size otherwise ("Red · 1 l"); `variantName()` in `@paint/shared` is the
one rule. Label changes are audited like renames. EAN/UPC barcodes are
check-digit validated. The catalogue is shared by all stores; stock per store comes next.
Brands, categories, products and pack sizes are deactivated rather than deleted, so history keeps
pointing at them: an inactive brand or category (or a subcategory of an inactive one) takes no new
products, and a product cannot move to one or be reactivated under one; existing products can still
be edited. The counter lookup leaves out discontinued products unless asked; the CSV import refuses
rows that would add products to an inactive brand or category. Renames and status changes are in the
audit log.

**Stock** (roadmap §3.13–3.16): every movement is a permanent, append-only ledger entry (a
database trigger refuses edits and deletes; corrections are new entries). Balances per store and
product change only through `postStockMovements()` in `@paint/db`, in the same transaction, with
exact decimal arithmetic and a weighted-average cost. Stock never goes negative.
`findStockMismatches()` compares balances with the ledger; the background worker runs it nightly
with the reservation, party-balance and allocation checks (one reconciliation per business per India
day, recorded with its findings; see `/reconciliation`).

**Transfers** (roadmap §3.15): requested → approved → in transit → received (or rejected /
cancelled). Each step moves the status only from the expected one, so double clicks and races
cannot apply a step twice. Dispatch and receipt post through `postStockMovements()`; damaged
units are written off at the destination and shortages stay on the transfer.

**Stock counts** (roadmap P1-M13): corrections are `counted − books at the start`, posted on
approval as `count_correction` ledger entries, so movements during the count are kept. The
person who submitted a count cannot approve it unless they have all-store access; counts name who
started and submitted them (`startedBy`, `submittedBy`) and `/auth/me` carries the `memberId`, so the
app can hide Approve from the submitter.

**Purchasing** (roadmap P1-M15, P1-M16): suppliers are parties with the supplier role. A purchase
order is open → partially received → received (or cancelled before anything arrives, or closed
short). Goods receipts (GRN-000001…) post `purchase_receipt` entries; scheme free units are a
separate entry at zero cost, so they lower the average cost. Receipts lock their order, so two
entered at once cannot over-receive, and a supplier's invoice number can be entered only once.
Each receipt records the supplier's latest cost for the next order.

**Imports** (roadmap P1-M17): CSV as Excel or Google Sheets saves it, up to 5,000 rows. A preview
saves nothing and lists every problem by row and column; committing saves all rows or none. Running
the same file again updates instead of duplicating: products match by SKU, parties by GSTIN or
mobile number, opening stock by store and SKU. An optional `variant_label` column names hardware
sizes: products are refused when they repeat a product's size, unit and label (in the file or
against saved packs), and on opening stock it must match the SKU's label, catching a mistyped SKU
among look-alike pieces. Blank cells keep saved values. Opening stock is
refused once a product has other movements at that store; use a stock count instead. The products
file names each product's tax category in `tax_category` (by name, any case; it replaced the old
`gst_percent` column): unknown or inactive categories are refused, and a blank one keeps the saved
category, or gives a new product the default until the business registers for GST, when it is required.

**Documents** (roadmap P1-M18): files attach to parties, products, stores, purchase orders, goods
receipts, transfers, stock counts, leads, opportunities, projects and contracts. Whoever can see the record sees its documents; whoever can
change it can add or remove them, and store access applies (a Pune order's documents are invisible to
Hyderabad staff). Every file is scanned by ClamAV before it is stored — including inside Word and
Excel archives — and refused if infected or if scanning is down. The type comes from the file's bytes,
not its name; names are cleaned of paths and direction tricks; downloads are always attachments with
`nosniff`, so an uploaded page can never run in our site. Bytes live in S3 (Mumbai) under
`<organization>/documents/<id>`.

**Notifications** (roadmap P1-M19): a transfer request goes to the sending store's stock managers,
a dispatch to the receiving store's, a submitted stock count to whoever else can approve it, and a
product falling to its reorder level to that store's stock managers — once per dip, grouped by
store. Never to the person who acted. Notifications are written in the same transaction as the
event; emails go to an outbox and the background worker (every `WORKER_INTERVAL_SECONDS`) sends
them over SMTP (Amazon SES in production, Mailpit locally at http://localhost:58025), retrying 4
times with growing gaps. Several servers can run the worker safely. Follow-ups remind their assignee
(see Activities below).

**Leads & opportunities** (roadmap P1-M07): a lead moves new → contacted → qualified, then converts
into an opportunity (discovery → proposal → negotiation → won / lost), or is won directly or lost
with a reason. Every change locks the record first, so two people acting at once cannot both
apply. Leads and opportunities belong to a store; staff see their stores' only.

**Projects & sites** (roadmap P1-M08): identified → survey → specification → quotation →
negotiation → order → execution → completed (or cancelled with a reason). A project links its
customer, any number of architects, contractors, painters and dealers, and the opportunity it came
from. Site photos are documents on the project (categories `before_photo`, `after_photo`, with a
note); documents also attach to leads and opportunities. No shade or tinting data until Phase 2.

**Contracts** (roadmap P1-M24): contractor, supplier, customer and dealer agreements as a record
with terms, dates, documents and status, not a legal engine. Draft → active → terminated (with a
reason) or renewed; an active contract past its end date (India time) shows as `expired` until it is
renewed or terminated. Renewing creates a new contract (new number, active, linked both ways via
`renewalOf` / `renewedBy`), by default starting the day after the old one ends and copying its
terms. The signed agreement is a document on the contract (record type `contract`). Contracts with
a store are visible to that store's staff; those without are business-wide. On the renewal date
the assignee is reminded once, in the app and by email (`contract_renewal_due`); moving the date
reminds again. Status, dates and value changes are in the audit log; the customer 360 and search
include contracts.

**Credit** (roadmap P1-M25, spec §3.21–3.22): each party has at most one credit profile: status
(none, active or on hold, with a reason), limit in paise, credit days and risk. Limits and days
change only through a credit request that someone with `credit:approve` (owners and admins) approves
or rejects; approvers at the party's store (or anywhere, for business-wide parties) are notified
(`credit_request_awaiting_approval`) and the requester hears the decision (`credit_request_decided`).
One request may wait per party. Approving a new limit for an account on hold keeps it on hold; staff
with `credit:manage` hold an account, approvers release it. The rule engine (`checkCredit` in
`@paint/shared`) blocks credit without a limit, on hold, or overdue beyond the configured days, and
otherwise decides by utilisation: up to 80 % normal, up to 100 % manager approval, above that owner
approval (configurable per business with `PUT /credit-rules`). Until billing (Release 2.0) calculates
exposure from invoices, what a party owes and how late it is are entered by hand
(`manualExposurePaise`, `overdueDays`). Changes to limits, days, status, holds and the rules are in the
audit log; the customer 360 shows the credit position.

**Credit enforcement** (MVP 3 round 1a, P2-M09; `docs/mvp-3/credit-and-receivables.md`): after
go-live a party's exposure is its ledger balance plus the unbilled value of its open postpaid orders
(the hand-entered figures are then read-only, in the API and by a trigger). Projected exposure is
checked when a postpaid order is confirmed and when an invoice is issued leaving money unpaid
(walk-in bills are paid in full; bills of postpaid orders were checked at confirm). Past the rules a
sale needs a credit approval: `checkCredit` decides the level, a manager (`credit:approve_sale`,
owners, admins and branch managers, at the sale's store) or the owner; the seller asks
(`credit_approval_requested` to the approvers) and the approver decides with a reason
(`credit_approval_decided` to the requester). While one waits the order cannot confirm and the bill
cannot issue; an approval is used only while it still covers the sale (level and projected exposure
no higher). An approver may still approve in the confirm or issue dialog, recorded as an approval
they gave; MVP 2's override columns are filled from the approval. Once a day per business the worker
puts active accounts overdue beyond the rules on an automatic hold (`credit_hold_runs`, advisory
lock per business, `credit_hold_applied`); releasing needs approval and may waive the overdue block
for up to 90 days. A contractor may have site accounts: a limit and status per project, whose
exposure (its documents on that project and its open orders there) is checked with the party's, the
stricter winning. Approvals, site accounts, the new hold columns and the approval used by an order or
invoice are in the audit log. Web: **Credit approvals** (`/credit/approvals`), the approval prompt on
orders and at the counter, live exposure and site accounts on the customer 360, and
`/site-accounts/:id`. Migrations 0069–0071 (the 0071 data migration grants `credit:approve_sale`).

**Collections and messages** (MVP 3 round 2a, P2-M11 and the messaging half of P2-M32;
`docs/mvp-3/credit-and-receivables.md` §3.5, §6.1, §6.2, §6.4): the **Collections** worklist
(`/collections`, `receivables:read`) lists each salesperson's customers with something overdue,
escalations and due promises first, then the oldest debt, with last contact, the open promise and the
next step; a promise to pay is recorded from a row or the customer 360 (`credit:manage`). Once a day,
between 09:00 and 20:00 India time, the worker settles promises from payments received (kept when
covered, broken after their date, a broken one escalated to the salesperson's branch managers and the
store's credit approvers, `promise_broken`) and queues the reminders the business's schedule
(`/collections/reminders`, `credit:approve`) asks for. Every message to a party goes through
`message_outbox` and only with the party's consent on that channel at its current address
(`messaging_consents`, append-only, recorded on the customer 360 after the notice in en / hi / te):
WhatsApp through a `MessagingProvider` (`MESSAGING_PROVIDER`: `log` until a BSP is chosen), SMS through
the SMS sender, email through SMTP, with retries; templates may be reworded per business
(`message_templates`). A statement can be shared as a stored, revocable link
(`/public/statements/:token`, 7 days, rate-limited); with a WhatsApp provider, **Send on WhatsApp** on
the statement queues it. New permission `receivables:read` (migration 0076). Migrations 0072–0076
(0072–0073: the painter-points schema for P2-M36, `loyalty_earn_rules` and the `influencer` ledger
kind).

**UPI payment links** (MVP 3 round 4a, the payment-link half of P2-M32;
`docs/mvp-3/credit-and-receivables.md` §3.6, §6.2): **Send payment link** on an invoice, the customer
360 and ledger and the collections worklist (`payments:manage`) asks for an invoice's outstanding,
the overdue bills, everything owed or an advance, by WhatsApp or a `wa.me` share; reminders and
statement shares carry a link too (`{{payLink}}`). The gateway's signed webhook
(`/webhooks/payment-links/:provider`, each event once) records the payment at the link's store by the
"UPI link" mode, with no member and no register, allocates it oldest first and keeps the rest as an
advance, tells the store's staff and sends the customer a receipt. Links are listed on the invoice,
the customer 360 and `/payment-links`. `PAYMENT_LINK_PROVIDER=log` makes test links paid on the web
app's `/pay/:reference` page. Migrations 0079–0080.

**Each shop's own Razorpay account and gateway refunds** (MVP 3 round 4c,
[docs/mvp-3/payment-links.md](docs/mvp-3/payment-links.md)): with `PAYMENT_LINK_PROVIDER=razorpay`
owners and admins connect their own Razorpay account under **Settings → Payment link settings**
(keys checked, then sealed with envelope encryption under `GATEWAY_CREDENTIALS_KEY`; only their last
four characters are ever shown) and paste the business's own webhook address
(`/webhooks/payment-links/razorpay/<reference>`). Links live 10 minutes and ask for at most
₹1,00,000 by default, net of the advance or for the bills' full outstanding, all settings of the
business. Money a link took that nothing was owed for is refunded through the gateway by itself,
booked as MVP 2 refunds (refund voucher, party ledger, Tally), retried, and kept as an advance with
staff told when it fails. Migrations 0081–0082.

**Payment-link validity** (MVP 3 round 6a, [PO-60], [PO-61]): links sent in messages (reminders,
statement shares, a link sent on WhatsApp) stay payable for the business's message validity, a day
by default; counter links keep theirs (10 minutes). With Razorpay neither may be under 15 minutes:
connecting raises a shorter one and says so, and links are recorded with the expiry Razorpay keeps.
Migrations 0090–0091.

**Brand statement reconciliation** (MVP 3 round 6a, P2-M34; `docs/mvp-3/credit-and-receivables.md`
§3.9, §6.3): under **Purchasing → Brand statements** owners and admins make a template for each
distributor's statement once, then upload each month's statement (CSV or Excel). Its lines are
matched with the distributor's GRNs (by invoice number, then date window and amount, with or without
GST) and the scheme money recorded for its brand; the screen lists both sides, amount differences,
lines we do not have and records it does not show, splits the difference between the brand's
balance and our books, and downloads the mismatches as CSV. Members match by hand, unmatch, explain,
or record a scheme credit note from its line in one step. Migrations 0088–0089.

**Loyalty** (roadmap P1-M26, spec §3.23): a party (typically a painter or contractor) gets a
loyalty account, optionally looked after by a salesperson. Points live only in an append-only ledger
(a trigger refuses edits and deletes; corrections are adjustments with a reason), so the balance is
always the sum of the entries and is never stored. Entries are purchases (points at the programme's
earn rate, default 1 point per ₹100, on an amount entered by hand until billing exists:
`manualPurchasePaise`), manual and campaign awards, redemptions, adjustments and expiries.
Redemptions and negative adjustments lock the account and can never take the balance below zero, and
redemptions respect the minimum. With `expiryDays` set, each entry that adds points expires that many
days later; points are used soonest-expiring first, and the background worker writes off unused expired
points once a day (expired points are also written off before any redemption, so they cannot be spent).
Tiers go by lifetime points earned; reaching a new one tells the account's salesperson
(`loyalty_tier_reached`). Programme changes, account status and every adjustment are in the audit log;
the customer 360 shows the points.

**Activities & follow-ups** (roadmap P1-M09): every call, visit and note is an activity on a party
(customer, contractor, dealer, supplier…), lead, opportunity or project, and access follows that
record. A follow-up's assignee is reminded once, in the app and by email, when it is within 15
minutes of due (`follow_up_due`); rescheduling reminds again.

**Customer 360** (roadmap P1-M06): `GET /parties/:id/overview` gathers everything linked to a party,
counting all and listing the latest ten of each. Sections the member has no permission for come back
as `null`, and leads, opportunities and projects are limited to the member's stores.

**Audit log** (roadmap P1-M20): database triggers record every change to prices, roles and their
permissions, members' roles, store access and active status, and stock adjustments, write-offs and
count corrections, with the watched columns' old and new values. No code path can skip it, and the
application can only read the log: it cannot add, edit or delete entries, and even the database owner
cannot change or empty it. Each request runs as its member (`runAsMember`), so entries name who acted;
background and setup work appears as system. Contracts and credit are audited too (see their sections).

**Search** (roadmap P1-M21): every word must match somewhere, exact matches (a SKU, barcode,
mobile number or document number) come first, and `%` and `_` are ordinary characters. Each group
appears only with its read permission and keeps to the member's stores. Trigram indexes (`pg_trgm`)
keep "contains" searches fast: about 40 ms through the API with 10,000 customers and products.

**Dashboard & reports** (roadmap P1-M22): the dashboard puts one row per store the member works at
on one screen, with totals; sections without permission come back as `null`. Reports filter by
store and India-time days (`from`, `to`), plus status, stage, source, movement type or supplier
where they apply. Money is shown in rupees, times in India time; CSV downloads include a BOM so
Excel shows ₹ correctly.

**Two-factor sign-in** (TOTP, RFC 6238, implemented in `apps/api/src/auth/totp.ts` and checked
against the RFC test vectors): after the password or SMS code, people with an authenticator app, and
owners and organization admins of businesses that require it (the default; `PUT /organization/security`),
get a `twoFactor` challenge instead of a session: a `pendingToken` valid for 5 minutes and 5 tries.
Refused codes answer 401 with a machine-readable `code` (`wrong_code` with `attemptsRemaining`,
`too_many_attempts`, or `expired` for a used, expired or unknown token).
Those without an app add one first (`setupRequired`); the first code confirms it and returns 10
one-time recovery codes, shown once and stored only as keyed hashes. Secrets are encrypted with
AES-256-GCM (key derived from `AUTH_SECRET`), each code works once, and one step of clock drift is
allowed. An owner can reset a member's two-factor sign-in (audited); support sessions are exempt and
cannot change it. Platform operators always sign in with an app. A new business's owner is signed in
at sign-up and adds the app at their next sign-in.

**Party merge:** `POST /parties/:id/merge` moves everything that pointed at a duplicate (leads, opportunities, projects
and project roles, contracts, purchase orders, goods receipts, supplier prices, activities, documents,
credit and loyalty) to the surviving party in one transaction, then deactivates the duplicate with
`mergedIntoId` so old links lead to the survivor. Roles are combined; one-per-party records (customer and
supplier profiles) keep the survivor's. Credit: refused when both have a request waiting, or both have a
profile and the duplicate's gives credit; otherwise the duplicate's profile moves if the survivor has none.
Loyalty: the duplicate's account moves if the survivor has none; otherwise its unused points move as
adjustments keeping their expiry dates and its account is closed. Only members with all-store access
merge; merges are audited. A guard test fails when a new table references parties without being handled.

**Branding** (white-label): each business can set its app name, primary and accent colours, light /
dark / system mode, corner radius, density and font. The API validates and normalises it with
`validateBranding` from `@paint/shared`, the same rules the web app uses, and answers which colours
`deriveTheme` had to adjust to stay readable. Changes are in the audit log.

**Logo and branded sign-in page** (white-label): owners and admins upload a logo under **Settings →
Appearance** (PNG, JPEG or WebP up to 1 MB and 2048 px a side). Like documents, its type comes from its
bytes and it is scanned by ClamAV before it is stored in S3 (`<organization>/branding/logo-<id>`;
replaced and removed logos keep their file for the audit trail). **SVG is refused**: it is a document
that can carry scripts, event handlers and links to other sites, and the logo is served from our own
origin; a sanitiser robust enough to trust would mean a server-side DOM and an allowlist to maintain,
for no gain over a PNG. The file is stored as uploaded, not re-encoded (no native image libraries); the
API reads its size from the header and refuses sizes outside 16–2048 px. It is served only through
`GET /public/branding/:slug/logo/:version` (`inline`, `nosniff`, `Content-Security-Policy:
default-src 'none'; sandbox`, cached for a year under an address that changes with every logo, with an
ETag), and shows in the header (on a light plate in dark mode), on the sign-in page and as the browser
tab's and home-screen icon (the installed app's manifest icon stays the product's).

Each business has a **slug**, its sign-in link name (`sharma-paints`): derived from its name when it is
created (`generate_organization_slug()` in migration 0048, numbered `-2`, `-3`… when taken, never a
reserved name), unique ignoring case, and changeable by its owners (audited). Its branded sign-in page
is **`/sign-in?b=<slug>`**: a query parameter rather than `/<slug>/sign-in`, so slugs can never collide
with the app's own routes (today's or future ones) and there is one sign-in route for the service
worker and the redirects. A future `<slug>.<domain>` address maps onto the same thing: the web app
reads the slug from the host name where it now reads `b` (the reserved names already cover `www`,
`api`, `admin` and the like). The page calls `GET /public/branding/:slug`, which reads only the app
name, theme and logo address, outside tenant scope like sign-in itself (row-level security is
unchanged), with one query and the same 404 whether the business is unknown or suspended. The device
remembers the business (`paint.sign-in-business`: the last link opened, or the business last signed in
to), so the plain `/sign-in` shows its look too. Signing in never depends on the slug: someone in
several businesses gets the usual chooser with the page's business first, and someone in one business
signs in to their own. Support views, refused support links and the platform console keep the
product's own look. The API has no rate limiter yet; the endpoint answers from one indexed query, and a
limit belongs in the load balancer or CDN in front of it.

**Shared response types:** the shapes the web app reads (`SessionGrant`, `AuthProfile`, `Dashboard`,
`SearchResults`, `NotificationPage`, `BrandingView`, …) live in `packages/shared/src/api.ts`; the API
returns them and the web app imports them, so the two cannot drift apart.

**Platform console** (roadmap P1-M23): operators sign in separately (their tokens and businesses'
tokens never work for each other). Businesses are on a plan (trial: 5 stores and 25 team members,
standard: 10 and 50, enterprise: unlimited; self sign-ups start on `SIGNUP_PLAN`) with per-business
feature flags. Suspending a business signs it out and blocks sign-in. Businesses may only rename
themselves: plan, flags and suspension are set by the platform, and every change is in the business's
audit log. Support access must be approved by the business's owners or admins, lasts 15 minutes to 8
hours, is read-only, can be ended by either side, and every request made with it is recorded for the
business to review.

## The first platform operator

Operators run the service from the platform console (`/platform`), apart from any business. The first
one is created once with a bootstrap token; the API refuses a second bootstrap.

```sh
# apps/api/.env: a long random secret (32+ characters), only for as long as you need it
echo "PLATFORM_BOOTSTRAP_TOKEN=$(openssl rand -hex 32)" >> apps/api/.env
pnpm --filter @paint/api build && pnpm --filter @paint/api start
curl -X POST localhost:3000/platform/bootstrap -H 'content-type: application/json' \
  -d '{"token":"<the token>","fullName":"Your Name","email":"you@example.com","password":"a long password"}'
```

Then remove `PLATFORM_BOOTSTRAP_TOKEN` from `apps/api/.env` and restart the API. Open
http://localhost:5173/platform (with `pnpm --filter @paint/web dev` running), sign in with that email and
password, and add an authenticator app from the QR code; every later sign-in asks for a code from it.
`pnpm demo` creates a demo operator instead (see Run the demo).

## Database

- Tables are defined in `packages/db/src/schema.ts`. After changing it, generate a migration with
  `pnpm --filter @paint/db db:generate` and commit the new file in `packages/db/migrations/`.
- Hand-written SQL (roles, grants, data fixes): `pnpm --filter @paint/db db:custom --name <what>`.
- **Tenant isolation:** every tenant query runs inside `withTenant(db, organizationId, work)`.
  PostgreSQL row-level security then limits it to that organisation's rows. Every table must
  enable row-level security with a policy; an integration test fails the build otherwise.

## Layout

```
apps/api              HTTP API (NestJS on Fastify), built with Vite into dist/server
apps/web              Web app (React + Vite PWA): sign-in (with two-factor), shell, dashboard, customers, credit, loyalty, team and roles, appearance, tax & GST, account security, support access, platform console
packages/ui           Design system: theme runtime and accessible components on design tokens
packages/db           PostgreSQL schema, migrations, tenant isolation (Drizzle)
packages/shared       code shared by all apps (money in paise, branding and theme derivation, …)
packages/testing      test helpers (throwaway PostgreSQL for integration tests)
packages/observability  error-report scrubbing shared by the API and web Sentry setup
packages/ops          one-off operations: migrations on deploy, the backup restore drill
infra/terraform       AWS (ap-south-1): staging and production, never applied from CI
docs                  architecture, environment variables, runbooks (deploy, restore, secrets, incidents)
```
