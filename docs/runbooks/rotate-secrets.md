# Rotating secrets

All secrets live in AWS Secrets Manager under `paint-<env>/…`. ECS reads them when a task
**starts**, so after changing one, start new tasks: `aws ecs update-service --cluster paint-<env>
--service api --force-new-deployment` (a rolling restart, no downtime). Rotate on a schedule
(yearly), when someone with access leaves, and immediately if a value may have leaked —
except `AUTH_SECRET`, which is rotated only after a leak ([why](#auth_secret)).

| Secret                                    | Generated by                          | How to rotate                                                                                                                                  | Effect on users                                                                                                       |
| ----------------------------------------- | ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `paint-<env>/database-url` (RDS password) | Terraform, ephemeral (never in state) | Increase `db_password_version`, apply, restart                                                                                                 | None if done as below                                                                                                 |
| `paint-<env>/auth-secret`                 | Terraform, ephemeral                  | **Only if it leaked** — read [AUTH_SECRET](#auth_secret) first                                                                                 | Sign-in codes already sent stop working; with two-factor sign-in, every authenticator and recovery code stops working |
| `paint-<env>/smtp-url` (SES)              | Terraform (IAM access key)            | `terraform apply -replace=…aws_iam_access_key.smtp`, restart                                                                                   | Emails pause for a minute; the worker retries                                                                         |
| Origin verify header (CloudFront → ALB)   | Terraform `random_password`           | `terraform apply -replace=module.stack.random_password.origin_verify`                                                                          | A few minutes of 403s while CloudFront updates (do it off-peak)                                                       |
| `paint-<env>/platform-bootstrap-token`    | Terraform, ephemeral                  | Only exists while `platform_bootstrap_enabled`; turn it off after use                                                                          | —                                                                                                                     |
| Sentry DSNs                               | Sentry                                | Create a new client key in Sentry, update Terraform `sentry_dsn` / the `WEB_SENTRY_DSN_*` variables, apply and deploy; then revoke the old key | —                                                                                                                     |
| `paint-<env>/gateway-credentials-key`     | By hand (`openssl rand -base64 32`)   | Read [GATEWAY_CREDENTIALS_KEY](#gateway_credentials_key) first                                                                                 | None: businesses' Razorpay keys keep working                                                                          |
| GitHub → AWS                              | none: OpenID Connect, no stored keys  | Nothing to rotate                                                                                                                              | —                                                                                                                     |

## Database password

Terraform writes the new password to RDS and the new `DATABASE_URL` to Secrets Manager in one
apply, but running tasks still hold the old password in their connections and environment:

1. Apply in a quiet period:
   ```sh
   cd infra/terraform/envs/prod
   terraform apply -var db_password_version=2      # or set it in terraform.tfvars
   ```
2. Immediately restart the API (`--force-new-deployment`) and wait for the service to be stable.
   Existing connections keep working until they are closed; new tasks connect with the new
   password. Expect a short burst of failed new connections from old tasks during the roll.
3. Commit the new version number in `terraform.tfvars` (it is not secret).

## AUTH_SECRET

`AUTH_SECRET` hashes one-time sign-in codes. With two-factor sign-in (backend branch
`backend/2fa-party-merge-search`) it also **derives the encryption key for authenticator (TOTP)
secrets and keys the recovery-code hashes**. There is no key versioning, so a new value means:

- codes sent before the restart stop verifying (people request a new one; harmless);
- **every enrolled authenticator app and every recovery code stops working.** Owners and admins of
  businesses that require two-factor sign-in, and all platform operators, can no longer sign in
  until their two-factor sign-in is reset and they enrol again.

Sessions are not affected (session tokens are random and stored hashed without the secret).

So do **not** rotate it on a schedule. Rotate only if it may have leaked, and plan it:

1. Agree a window and tell owners they will set up their authenticator again.
2. Rotate:
   ```sh
   terraform apply -var auth_secret_version=2      # then commit the number in terraform.tfvars
   aws ecs update-service --cluster paint-prod --service api --force-new-deployment
   ```
3. Reset two-factor sign-in for the affected people (as a platform operator, or with a reviewed SQL
   script against the two-factor tables written by the backend track), so they enrol at their next
   sign-in.

Follow-up for the backend track: give the two-factor encryption its own versioned key (for example
`TOTP_ENCRYPTION_KEYS` holding the current and previous keys) so either secret can be rotated
without locking people out.

## SES SMTP credentials

```sh
terraform apply -replace='module.stack.module.email.aws_iam_access_key.smtp'
aws ecs update-service --cluster paint-prod --service api --force-new-deployment
```

Emails queued while tasks restart are sent by the worker on its next run (it retries failures).

## GATEWAY_CREDENTIALS_KEY

It wraps the data keys that seal each business's Razorpay keys for payment links
([payment-links.md](../mvp-3/payment-links.md#3-credentials-security-design)). Losing it loses
every business's connection (they reconnect with their keys); rotating it loses nothing:

1. Keep the current value: `aws secretsmanager get-secret-value --secret-id
paint-<env>/gateway-credentials-key`.
2. Create a `paint-<env>/gateway-credentials-previous-key` secret with that value, and add it to
   the API task as `GATEWAY_CREDENTIALS_PREVIOUS_KEY` (a Terraform change to the api module's
   `api_secrets`, applied).
3. Put a new value in: `aws secretsmanager put-secret-value --secret-id
paint-<env>/gateway-credentials-key --secret-string "$(openssl rand -base64 32)"`, then restart.
4. Each business's keys are sealed again under the new key the next time they are used (a link, a
   refund, the settings page). When no row is sealed under the old key any more, remove the
   previous key and restart:
   ```sql
   select count(*) from payment_gateway_accounts
   where credentials_sealed is not null and split_part(credentials_sealed, ':', 2) <> '<new key id>';
   ```
   (The key id is the first 12 hex characters of HMAC-SHA256(key, `paint:gateway-credentials:key-id`).)

If the key leaked, the sealed rows alone are still useless without database access; rotate as above
and ask businesses to roll their Razorpay keys if the database leaked too.

## If a secret leaked

1. Rotate it as above, now.
2. Database: also review `pg_stat_activity` and the PostgreSQL log in CloudWatch for unknown
   clients; the database is not reachable from the internet (private subnets, security group).
3. SES: check the SES sending statistics for unexpected volume.
4. Record what happened ([incident.md](incident.md)).
